# 注册中心 v3：把「类型」补成数据

> 状态：**构思稿，未实现**
> 记录时间：2026-10-25
>
> 这份文档只做一件事：把 v2 里「缺一个 type」这个判断写清楚，并给出可能的方向。
> 不承诺实现，也不代表已经定稿。

## 一句话

v2 的 `data[owner]` 有三个库 —— `meta`（清单）、`declares`（接口契约）、
`registers`（条目）。**缺第四个：`types`（条目可以长成什么样）**。

结果是「结构」没法被定义，只能靠宿主代码里的 if-else 和旁路集合去模拟。

## 现状：结构是硬编码的

### 证据一：`_exec` 里靠字符串分派

```python
def _exec(self, verb, name, fields, fn):
    actor = self._actor()
    if self.name == "settings":
        return self._settings(verb, name, fields, actor, fn)
    if self.name == "signals":
        return self._signals(verb, name, fields, actor, fn)
    if self.name == "tools":
        return self._tools(verb, name, fields, actor, fn)
    return self._registry(verb, name, fields, fn, actor)
```

`self.name` 是接口路径的**最后一段**。所以：

- `core/signals` 走 `_signals`，`myplugin/signals` 也走 `_signals`
- 插件想定义自己的 `mysignals` —— 不行，除非改宿主
- 插件想把某个点叫 `tools` —— 会被劫持

`core/signals` 甚至不是 registry 里的接口（`declared("core/signals")` 为 False），
它只靠这个字符串匹配存在。

### 证据二：层级靠模块级集合旁路记账

```python
# registrar.py
_SETTINGS_POINTS = set()          # 不在 registry 数据里

def _declare_settings_point(owner, segs):
    _SETTINGS_POINTS.add((owner, tuple(segs)))

def _require_settings_points(owner, segs, where):
    for i in range(1, len(segs) + 1):
        if (owner, tuple(segs[:i])) in _SETTINGS_POINTS:
            continue
        pre = _settings_point_path(owner, segs[:i])
        raise KeyError(f"{where!r}: 设置点 {pre!r} 还没注册")
```

`core/settings&launcher&java` 的父子关系完全由这个集合 + 字符串拼接维护，
registry 本身对层级一无所知。这样带来三个后果：

- 层级关系没法查询（只能问 `settings_points()` 这个私有函数）
- 层级关系没法校验（除了 `_require_settings_points` 那一条路径）
- 层级关系没法序列化（`dump()` 里看不到）

### 证据三：`kind` 是个死参数

```python
# registry.py:320  声明时收下
built=(), kind="class", doc="", callingMode=None, override=True
# registry.py:365  写进契约
"kind": kind,
# 全项目：没有任何地方读它
```

位置早就留好了，但那个库不存在。

## 目标

让「这类条目长什么样」成为**数据**，而不是宿主代码。

理想状态：

- 插件能定义自己的条目结构，宿主不认识也能存、能查、能渲染
- 内置的 `settings` / `signals` / `tools` 和插件的自定义类型走同一套机制
- `_SETTINGS_POINTS` 这类旁路集合可以删掉

## 方向（未定稿）

### 核心：`types` 库

```python
data[owner] = {
    "meta": {},        # 清单
    "declares": {},    # 接口契约
    "registers": {},   # 条目
    "types": {},       # ← 新增：条目结构
}
```

### type 定义

```python
registry.type("core/settings",
              fields=("default", "title"),      # 成员：条目能带哪些字段
              children=("core/settings",))      # 能嵌哪些子类型（递归）

registry.type("core/tools",
              fields=("obj",),
              children=())                      # 空元组 = 明确不许嵌套
```

`children` 里写的是 type 路径 —— **「type 里套 type」就是靠这个一字段表达的**，
不需要真的用 Python class。

### 接口绑 type

```python
registry.declare("core/settings", type="core/settings", ...)
```

### 条目可以带 type，默认继承

```python
add("core/settings", "core/launcher", title="启动器")          # 继承接口的 type
add("core/settings", "core/launcher/java", title="Java")      # 同上
add("core/settings", "core/launcher/x", type="core/tools")    # 显式覆盖
```

子条目的类型 = 最近一层祖先条目的类型；写 `type=` 时覆盖。

## 待定的三个问题

这三个不定，实现会跑偏。**留到实现时再决**。

### ① 行为要不要也进 type？

type 只管结构的话，`signals` 的 `emit`/`connect`、`settings` 的 `other()`
仍然得留在 `registrar.py` 里，`_exec` 的 if 也还在。那就是「插件能定义结构，
但不能定义行为」。

三个选项：

| 方案 | 形态 | 开放程度 |
|---|---|---|
| A | `type(fields=, children=, handler=)` —— 结构和行为都在 type 里 | 最高 |
| B | type 只管结构，`_exec` 的 if 保留 | 最低 |
| C | `type(...)` 和 `handler(...)` 分开注册 | 中 |

用户倾向：type 是结构（类比 struct），不是 class。**但那样行为就还锁在宿主里**，
这一点需要在实现前想清楚能不能接受。

### ② 父级必须先存在吗？

```python
add("core/settings", "core/launcher", title="启动器")
add("core/settings", "core/launcher/java", title="Java")   # 父级必须已登记吗？
```

如果 type 能管这件事，`_SETTINGS_POINTS` 就可以删掉 —— 这是 v3 最实在的收益。

### ③ 访问即嵌套 vs 一次写多层路径

```python
# 写法一：一次写两层
add("core/settings", "core/launcher/java", title="Java")

# 写法二：访问即嵌套
Register("core/settings&launcher").add("java", title="Java")
```

两种都支持，还是只留一种？

## 为什么不在现在做

这是**开放式插件系统的地基**，不是一处修补：

- 改动面覆盖 `registry.py`（存储 + 校验）、`registrar.py`（分派）、
  所有 `declare()` 调用点（15 处）、`_SETTINGS_POINTS` 的拆除
- 没有测试覆盖（`scripts/` 被 `.gitignore` 排除，仓库里一条测试都没有）
- 一旦做半套，会比现在更难维护

适合在测试齐全、能跑完整回归的环境里做。

## 与当前分支的关系

`review-Book` 上已经修的是**明确的 bug**，与 v3 无关：

- `watch` / `owned` 动词实参位置传错（功能完全失效）
- `&` / `#` 的 owner 补全延迟到下一段（`#` 从不生效）
- `_sub_point` 让条目链变成子接口（同一句两种落点）

这些修完，v3 的起点更干净。

## 附：v2 已经做对的部分

v3 不该动这些：

- **归属即桶**：条目长在谁的 `registers` 下就是谁登记的，卸载 = 删一棵子树
- **接口与内容分区**：`declares` 只有契约，`registers` 只有内容
- **覆盖是一条栈**：被顶掉的留在下面，顶的人走了自动回退
- **先全校验再落盘**：`commit` 里 `_validate_stage` 在写正表之前跑

v3 只补 `types` 这一个库，以及由此带来的层级表达能力。

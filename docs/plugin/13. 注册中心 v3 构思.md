# 注册中心 v3：type 是一个带公开面的类

> 状态：**构思稿，未实现**
> 记录时间：2026-10-25
>
> 这份文档只做一件事：把 v2 里「缺一个 type」这个判断写清楚，并给出可能的方向。
> 不承诺实现，也不代表已经定稿。

## 一句话

v2 的 `data[owner]` 有三个库 —— `meta`（清单）、`declares`（接口契约）、
`registers`（条目）。缺的是**类型**：接口绑的到底是什么东西。

缺了它，「结构」和「用法」都没法被定义，只能靠宿主代码里的 if-else
和模块级旁路集合去模拟。

## 现状：类型是硬编码的

### 证据一：`_exec` 里靠字符串分派

```python
def _exec(self, verb, name, fields, fn):
    actor = self._actor()
    if self.name == "settings":
        return self._settings(verb, name, fields, actor, fn)
    if self.name == "signals":
        return self._signals(verb, name, fields, actor, fn)
    if self.name == "tools":
        return self._tools(verb, name, fields, actor, fn)
    return self._registry(verb, name, fields, fn, actor)
```

`self.name` 是接口路径的**最后一段**。所以：

- `core/signals` 走 `_signals`，`myplugin/signals` 也走 `_signals`
- 插件想定义自己的 `mysignals` —— 不行，除非改宿主
- 插件想把某个点叫 `tools` —— 会被劫持

`core/signals` 甚至不是 registry 里的接口（`declared("core/signals")` 为 False），
它只靠这个字符串匹配存在。

### 证据二：层级靠模块级集合旁路记账

```python
# registrar.py
_SETTINGS_POINTS = set()          # 不在 registry 数据里

def _declare_settings_point(owner, segs):
    _SETTINGS_POINTS.add((owner, tuple(segs)))

def _require_settings_points(owner, segs, where):
    for i in range(1, len(segs) + 1):
        if (owner, tuple(segs[:i])) in _SETTINGS_POINTS:
            continue
        pre = _settings_point_path(owner, segs[:i])
        raise KeyError(f"{where!r}: 设置点 {pre!r} 还没注册")
```

`core/settings&launcher&java` 的父子关系完全由这个集合 + 字符串拼接维护，
registry 本身对层级一无所知。三个后果：

- 层级关系没法查询（只能问 `settings_points()` 这个私有函数）
- 层级关系没法校验（除了 `_require_settings_points` 那一条路径）
- 层级关系没法序列化（`dump()` 里看不到）

### 证据三：`kind` 是个死参数

```python
# registry.py:320  声明时收下
built=(), kind="class", doc="", callingMode=None, override=True
# registry.py:365  写进契约
"kind": kind,
# 全项目：没有任何地方读它
```

位置早就留好了，但那个东西不存在。

## 目标

让「这个接口是什么、能怎么用」成为**可注册的东西**，而不是宿主里的 if。

理想状态：

- 插件能定义自己的类型（结构 + 用法），宿主不认识也能存、能查、能调用
- 内置的 `settings` / `signals` / `tools` 和插件的自定义类型走同一套机制
- `register(...)` 产出的是 Point 子类实例 —— Point 是 registrar 的根类型，
  自带条目表与更新信号；其它类型靠继承它拿到这些，不另装 signal 子类型
- `_SETTINGS_POINTS` 这类旁路集合可以删掉

## 方向：type 是一个类

### 不用新开存储库

`declare` 的契约块本身就是个 dict，class 直接放进去：

```python
@registry.type("core/signals")
class Signals:
    ...
```

```python
# 契约块大致长这样
{
  "fields": ("payload", "doc"),
  "required": (),
  "built": ("obj",),
  "type": Signals,          # ← 就是类本身
  ...
}
```

条目、契约、类型各居其位，不需要第四个库。

### 公开面用装饰器标出

类里哪些方法可以被 `register(...)` 调用，由装饰器声明：

```python
@registry.type("core/signals")
class Signals:

    def __init__(self, scope):
        self._scope = scope

    @public
    def emit(self, *args):
        """register("core/signals&on_start").emit()"""

    @public
    def connect(self, fn):
        """register("core/signals&on_start").connect(cb)"""

    @public
    @property
    def name(self):
        """register("core/signals&on_start").name  →  "core.on_start" """

    # 不标的属于内部，外部调不到
    def _bus(self):
        ...
```

于是 `register("core/signals&on_start").emit(...)` 的路径是：

1. 查路径 → 接口 `core/signals` + scope `on_start`
2. 查契约 → `type` = `Signals`
3. 造实例／复用已造好的
4. 校验 `emit` 被 `@public` 标过
5. 调用

**加动词 = 在类里加一个方法**，不用改宿主。

### 实例存哪：`built`

不需要新机制 —— `built` 已经是容器槽位，`provide()` 用的就是它：

```python
# registry.py 现有代码
def bind(self, point, key, **built):
    top.setdefault("built", {})
    top["built"].update(built)          # 实例落在这里

def provide(self, point, key, obj, **meta):
    self.add(point, key, **dict(meta, init=lambda b: obj))
    return self.bind(point, key, obj=obj)
```

`core/tools` 现在就是这个形态：活对象塞进 `built.obj`，`get` 取出来。
type 的实例同理，只是由接口自己负责造。

### 层级：条目套条目

父子关系就是 key 的路径，不需要额外的 tree 结构：

```python
add("core/settings", "core/launcher", title="启动器")
add("core/settings", "core/launcher/java", title="Java")
```

`core/launcher/java` 的父级是 `core/launcher`。类型默认继承最近一层祖先，
写 `type=` 时覆盖。

`Settings` 类可以自己决定怎么呈现子项：

```python
@registry.type("core/settings")
class Settings:
    def __init__(self, scope):
        self._scope = scope

    @public
    def get(self, key):
        ...

    @public
    def other(self, owner):
        """跨桶读"""
        ...

    @public
    def __getitem__(self, key):
        """settings["theme"] —— 省掉 .get()"""

    @public
    def __iter__(self):
        """for k in settings: ..."""
```

### Point 是 register 的亲儿子

`core/Point` 不是一个普通接口，它是 **registrar 体系的根类型** ——
`register(路径)` 产出的就是 Point（或其子类）的实例。

现在的代码里，`register()` 返回 `Scope`：

```python
# registrar.py:565
def registrar(path):
    return Scope(path)
```

`Scope` 干的事就是「一个可注册的点」：持路径、持 owner、按动词读写注册表。
v3 只是把它**类型化** —— 从「动词分派器」变成「有类型的注册点」：

```
现在：  register("core/setting/item") → Scope  →  查 _exec 的 if → 走某个 _xxx 方法
v3：    register("core/setting/item") → Point 子类实例 → 调它自己的方法
```

所以：

- Point 自带条目表和更新信号 —— 因为「注册点」的本质就是「能存条目、能通知」
- `SettingItem(core.Point)` 是「一个注册点 + 两个字符串字段」—— 它是 Point 的子类
- 不需要 compose 一个 signal —— 注册点本来就会通知，这是它的天性

继承链：

```
core/Point                      能存条目 + 能通知（所有注册点的底座）
    ├── core/setting/item        + title, icon
    ├── core/settings            
    ├── core/signals             + 动作：emit / connect
    └── myplugin/storage         + 动作：read / write（插件自带）
```

#### 它自带什么

| 自带 | 干什么 | 现在对应什么 |
|---|---|---|
| 条目表 | 存注册项、按 key 取 | `registers` 树 + `add/set/get/remove` |
| 更新信号 | 条目增删改时通知订阅者 | `registry.watch()` / `_notify()` |
| 产物槽位 | 挂活对象、按名取回 | `built` + `bind`/`provide` |

**更新信号不用另装一个 signal 子类型** —— 它就在 Point 身上。于是设置页的
条目注册点只剩两个字段：

```python
@registry.type("core/setting/item")
class SettingItem(core.Point):      # 继承：条目表 + 更新信号
    """设置页里的一条注册项。

    自己不写逻辑 —— 两个字符串字段，其余全来自 core/Point。
    """
    title: str      # 标题
    icon:  str      # 图标路径
```

用起来：

```python
item = register("core/setting/item&theme")

item.title                     # string 字段
item.icon                      # string 字段
item.add(key, ...)             # 继承自 Point：存注册项
item.watch(cb)                 # 继承自 Point：条目一变就通知 → 设置界面重建
```

外面看到的是一个对象，实际是「Point 的底座 + 两个字符串」。**没有 compose。**

对应到现在代码里的东西：

| v3 概念 | 现在在哪儿 |
|---|---|
| `core/Point` 的条目表 | `registers` 树 + `add/set/get/remove` |
| `core/Point` 的更新信号 | `registry.watch()` + `_notify()`（已在用） |
| `core/Point` 的产物槽位 | `built`（`bind` / `provide`） |
| `title` / `icon` 两个 string | 条目字段 `title` / `icon` |

现在这些是散的：字段靠 `declare(fields=...)`、通知靠 `registry.watch`、
产物靠 `built`。继承 Point 把它们收到一个类型里。

> 注：`compose`（装载另一个类型）这个概念在这一轮讨论后被去掉了 ——
> 原本想用它装 `signal`，但信号就是 Point 自带的更新通知，不必另立门户。
> 若将来真需要「装一个与 Point 无关的类型」，再单独议。

### 命名空间根也是一个 Point

既然 Point 就是 register 的亲儿子，那**命名空间根本身也可以是一个 Point**：

```
core                          一个 Point，允许挂任意类型的子 Point
 ├── core/setting              Point（设置点）
 │    └── core/setting/item     Point（+ title, icon）
 ├── core/pages                Point
 ├── core/signals              Point（+ emit / connect）
 └── myplugin/...              插件挂进来的
```

于是点树和路径是**同一棵树** —— 路径即位置，不需要另建 tree 结构：

```
register("core")                 根点，能挂任何类型
register("core/setting")         它的子点
register("core/setting/item")    子子点
```

这条成立的话，`add("core/setting/item", ...)` 里的父级存在性检查也就自然了：
`core/setting/item` 的父是 `core/setting`，再上一级是 `core`。**待定项 ④
（父级是否必须先存在）可以靠这个回答** —— 父级必须存在，因为那就是树。

### 「any 类型」需要两处改动

现在这两条硬约束挡住了它，都是查证过的：

**① 命名空间根还不能当接口**

```python
>>> _split_point("core")
RegistryError: 接口 'core' 不合法：要写成 <owner>/<接口名>（如 core/pages）
```

`_split_point` 要求 `owner/name` 两段。要允许单段路径当点，得放开这条。

**② `fields=()` 表示「一个字段都不许」，不是「任意」**

```python
>>> r.declare("core/x", fields=())
>>> r.add("core/x", "core/a", anything=1)
RegistryError: core/x#core/a: 未知字段 ['anything']；该接口只接受 []
```

`_check_write` 里 `unknown = sorted(set(fields) - allowed)`，`allowed` 是空集，
所以任何字段都会被拒。要表达「任意」，需要一个显式哨兵（`fields=None`
或 `fields="*"`），不能沿用空元组。

同理，Point 的 `children` 也需要一个「任意类型」的写法 —— 而它天然存在：
`children=any` 就是「任何以 Point 为祖先的类型」。

### 注册点被调用时的流程

现在是三套后端各走各的：`core/settings` 写 `plugin.settings`、`core/signals`
写 `events` 总线、`core/tools` 写 `registry.data`。分派靠 `_exec` 的三个 if。

统一之后，所有 type 走同一条流程 —— **先落 Point，再激活 signal**：

```
register("core/setting/item&theme").new(title="主题", icon="…")
        │
        ├─ ① Point 收下条目            ← 唯一真相，纯数据，可 dump / 可回退
        │     point.add("core/theme", title="主题", icon="…")
        │
        ├─ ② type 处理数据（钩子）      ← 可选，各 type 自己写
        │     SettingItem.on_store(key, fields)
        │
        └─ ③ 激活 signal                ← 通知订阅者
              item.signal.emit()
```

于是 `_exec` 的 if-else 消失，改成「查契约 → 拿 type → 交给 Point 走流程」。
后端差异从**分派依据**降级成**钩子里的副作用**：

| type | `on_store` 里做什么 |
|---|---|
| `SettingItem` | 值同步进 `plugin.settings`，登记设置页控件 |
| `Signal` | 名字注册进 `events` 总线 |
| `Tool` | 活对象塞进 `built.obj` |
| 默认（`core/Point`） | 什么都不做，条目留在 Point 里就完事 |

三条约束：

1. **钩子失败必须能回滚** —— 先落 Point 再处理，处理失败要把那条撤回，
   否则留下半成品。加载会话（`begin` / `commit` / `abort`）已经是这个语义：
   钩子抛异常 → 会话 abort。
2. **Point 里永远是纯数据** —— `built` 的实例只是缓存，`commit`/`abort`、
   覆盖弹栈、`remove_namespace`、插件重载时全部丢弃。
3. **钩子是一组不是一个** —— `on_store` / `on_update` / `on_remove` / `on_build`
   分开；`on_build` 就是现在每条目各写一个 `init` 的那个位置。

### 能吃到 Python 的现成轮子

这是这条路最大的好处 —— 宿主不用重新发明：

| Python 机制 | 在 type 里表达什么 |
|---|---|
| `__init__` | 拿到 scope，造出实例 |
| `@property` | 只读访问点（`signals.name`） |
| `__getitem__` / `__setitem__` | `settings["theme"]` |
| `__call__` | `tool(...)` 直接调用 |
| `__iter__` / `__len__` | 遍历、`len()` |
| `__enter__` / `__exit__` | `with register("core/db").tx():` |
| `__getattr__` | 动态子项（取不存在的名字自动嵌套） |
| 继承 / `super()` | `class MySignals(Signals)` 改一点行为 |
| `@classmethod` / `@staticmethod` | 类级操作 |
| `abc.ABC` + `@abstractmethod` | 强制子类实现 |
| `@dataclass` | 字段声明自动化 |

### 内置三个的迁移

```python
@registry.type("core/signals")
class Signals:
    @public
    def emit(self, *args): ...
    @public
    def connect(self, fn): ...

@registry.type("core/settings")
class Settings:
    @public
    def get(self, key): ...
    @public
    def other(self, owner): ...     # 跨桶读

@registry.type("core/tools")
class Tools:
    @public
    def get(self, name=None): ...   # 取活对象
    @public
    def __getitem__(self, name): ...
```

`registrar.py` 里 `_settings` / `_signals` / `_tools` 三个方法（约 250 行）
搬成三个类，`_exec` 的 if-else 换成一次「查契约 → 拿 type → 找方法」。

### 插件定义自己的类型

```python
from BMLCore import registry, public

@registry.type("myplugin/storage")
class Storage:
    def __init__(self, scope):
        self._scope = scope

    @public
    def read(self, key):
        ...

    @public
    def write(self, key, value):
        ...
```

```python
registry.declare("myplugin/storage", type=Storage, fields=("path",))
registry.add("myplugin/storage", "myplugin/main", path="data/main.json")
```

之后 `register("myplugin/storage&main").read("theme")` 就能用了 ——
**宿主完全不认识 `Storage`**。

### 设置项的构造也是同一个位置

现在每个条目各写一个 `init`：

```python
registry.add("core.setting.items", "core.setting.theme",
             init=simple(Bool), section=..., order=20, title=...)
registry.add("core.setting.items", "core.setting.lang",
             init=simple(Combo), section=..., order=30, title=...)
```

v3 提到类型上，条目只写自己的数据：

```python
@registry.type("core/bool")
class BoolSpec:
    @public
    def build(self, box):
        return Bool(box.parent, box.title)

registry.add("core.setting.items", "core.theme", type="core/bool", ...)
```

消费者（`setting.py` 的 `_add_section`）只认「按 type 找构造器」，
不需要认识 `Bool` / `Combo` 这些具体类。

## 待定的问题

这几个不定，实现会跑偏。**留到实现时再决**。

### ① `scope` 里给什么

`__init__(self, scope)` 的 scope 至少要能给：

- 当前接口路径、当前条目 key、当前 actor
- 一个「往注册表读写自己的条目」的入口
- 对 `core/signals` 来说，还要能拿到事件总线

现有 `registrar.Scope` 差不多是这个东西，可能直接传进去。但它是 registrar
的内部类型，让插件类依赖它需要先把接口定下来。

### ② `@public` 的判定方式

- 纯方法名匹配：`register(...).emit()` → `class.emit`，只校验有没有 `@public`
- 还是 `@public(verb="emit")` 显式绑定到某个 DSL 动词

魔法方法（`__getitem__` / `__call__` / `__iter__`）要不要自动公开？
自动公开更 Python，但泄露面更大。

### ③ 实例的生命周期

- 每次访问新建（无状态，简单，但重复构造）
- 按 `(type, key, actor)` 缓存进 `built`（有状态，需要清理时机 ——
  卸载、插件重载、会话 abort 时怎么清）

`built` 已经是容器，缓存的位置现成，但「什么时候清」要定。

### ④ 父级必须先存在吗

```python
add("core/settings", "core/launcher", title="启动器")
add("core/settings", "core/launcher/java", title="Java")   # 父级必须已登记吗？
```

如果类型能管这件事，`_SETTINGS_POINTS` 就可以删掉 —— 这是 v3 最实在的收益。

### ⑤ `@registry.type` 何时执行

插件的类定义期就要调用它，那时代码还没进加载会话。需要确认：

- 类注册进正表（永久）还是进暂存区（跟随插件卸载）
- 装饰器在类定义期跑，此时 `registry.begin()` 可能还没开始

### ⑥ `core/Point` 到底自带什么

它是所有类型的底座，边界要先划清。目前设想的三样：

| 自带 | 含义 | 现在对应什么 |
|---|---|---|
| 条目表 | 能登记子条目、能按 key 取 | `registers` 树 + `add/set/get/remove` |
| 更新信号 | 增删改时通知 | `registry.watch()` / `_notify()` |
| 产物槽位 | 能挂活对象、能按名取回 | `built` + `bind`/`provide` |

需要定：

- **子类型继承 Point 时，拿到的是同一棵条目树，还是自己的一棵？**
  `SettingItem` 的条目要不要和父级隔离？
- 产物槽位只存「构建产物」，还是也接受任意运行期状态？
- 条目和产物槽位是同一个维度还是两个？（现在的 `built` 挂在条目上）

第一条影响最大：如果继承后共用同一棵树，`core/setting/item` 下面的条目和
`core/settings` 下面的条目会混在一起；如果各有一棵，`SettingItem` 就是
一个独立的登记区，这也更符合「注册点只有一个职责」的直觉。

## 为什么不在现在做

这是**开放式插件系统的地基**，不是一处修补：

- 改动面覆盖 `registry.py`（契约 + `built` 的用法）、`registrar.py`
  （250 行搬成类）、所有 `declare()` 调用点（15 处）、`_SETTINGS_POINTS` 的拆除
- 没有测试覆盖（`scripts/` 被 `.gitignore` 排除，仓库里一条测试都没有）
- 一旦做半套，会比现在更难维护

适合在测试齐全、能跑完整回归的环境里做。

## 与当前分支的关系

`review-Book` 上已经修的是**明确的 bug**，与 v3 无关：

- `watch` / `owned` 动词实参位置传错（功能完全失效）
- `&` / `#` 的 owner 补全延迟到下一段（`#` 从不生效）
- `_sub_point` 让条目链变成子接口（同一句两种落点）

这些修完，v3 的起点更干净。

## 附：v2 已经做对的部分

v3 不该动这些：

- **归属即桶**：条目长在谁的 `registers` 下就是谁登记的，卸载 = 删一棵子树
- **接口与内容分区**：`declares` 只有契约，`registers` 只有内容
- **覆盖是一条栈**：被顶掉的留在下面，顶的人走了自动回退
- **先全校验再落盘**：`commit` 里 `_validate_stage` 在写正表之前跑
- **`built` 是条目自带的容器**：`provide` / `bind` 已经在用它存活对象

v3 只补「类型」这一层，以及由它带来的结构表达与用法开放。

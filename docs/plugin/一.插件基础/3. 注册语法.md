# 一.插件基础 | 3.注册语法

> 📌 **命令式用 `register`，装饰器用 `registrar`**。新插件一律用 v3 写法；
> `registrar(...)` 解析不到 v3 路径时会回退旧 v2 作用域（过渡期行为）。

## register()：拿自己的点

```python
from BMLCore import register

me = register()      # 当前 owner 自己的点（插件加载期 = 你的插件）
```

`register(path)` 按 key 找人：先自己点 → 再 core 点 → 再逐段往下：

```python
register("core/log")          # 宿主登记的 BLog
register("parts")             # 自己点下的子项
register("core/settings")     # 宿主设置（BSettings）
```

## add()：往点上加东西

| 参数 | 作用 |
|---|---|
| `顺序名` | 条目 key（同 key 反复 add 拿同一个实例） |
| `type=` | 要建的类型：`core/point`（子点）、`core/signal`（信号）、`core/value`（值）… |
| `entry=` | 子点的默认条目类型（子点以后 add 出来的东西按它建） |
| 其余 `**fields` | 直接成为条目属性（`title` / `icon` …） |

```python
parts = me.add("parts", type="core/point", entry="core/value")
parts.add("greeting").set("你好")

group = me.add("group", type="core/point", title="我的组", icon="x.png")
```

## 路径分隔：`#` / `&`

只有两个链分隔符，都表示「往下走一层」，不是目录分隔符：

- `#` 从自己这条往下找；`&` 从上一段所在的宿主点往下找；
- 例：`register("core/settings&launcher&java")` 往宿主点上找/加；
- **`$` 不是有效语法**（历史上是 `&` 的误打，已从解析里删掉，现在写 `$` 会直接解析失败）。

> 📌 点名的层级用 `.`（`core.setting.items` 这种旧写法注册表会自动归一成 `/`），
> 条目 key 才是 `<owner>/<名字>` —— owner 永远是第一段。

## registrar(path)：装饰器专用

```python
from BMLCore import registrar

@registrar("core/signals&on_game_start").connect()
def on_start(*args):
    ...

@registrar("settings&java&select_java.value_changed").connect()
def on_select(value=None):
    ...
```

- `.connect()` 不带回调 → 返回装饰器；带回调 → 直接订阅
- `.emit(...)` 直接发
- 其它能力透传：`registrar("core/log").info("…")`

## 加载会话

加载器在插件构造前开会话：构造期间 `add` 先暂存，构造成功才提交；
构造中途抛异常 → 整场登记回滚（见[生命周期](4.%20生命周期.md)）。

> 📌 构造里写的登记此时「别人还看不到」；不要在里面自己 `unload` 自己。

## 常见错误

| 报错 | 原因 |
|---|---|
| `KeyError: core xxx 下没有条目 'yyy'` | 路径拼错 / 宿主没登记 / 你还没 add |
| `不收 'xxx' 类型的条目` | 子点的 `entry=` 或 `point` 接受表不允许 |
| `缺必填字段` / `未知字段` | 登记进有契约的点时字段不对 |
| `注册点 'core/settings&launcher' 还没注册` | v2 路径语法下，宿主设置点没先 `contract()` |

## 点与条目：谁决定“怎么登记”

记一句话：**`add` 只把东西交给点，怎么解释由点决定**。点在类内部用两个标记声明自己
开放哪些入口：

```python
class BDownloadPoint(BPoint):
    @decor                            # 装饰器入口：接收被装饰的对象
    def add(self, obj, name, **meta):
        ...

    @func                             # 直接入口：只收名字（纯条目点就是这个形态）
    def add(self, name, *types):
        ...
```

- 没标记的方法 = **内部函数**，外部（`register` / `registrar`）都调不到；
- `@decor` 的方法：签名是 `add(self, obj, name, **meta)` —— **第二个参数就是被装饰的
  类/函数**（第一个是 `self`）；
- `@func` 的方法：签名是 `add(self, name, *args)`，不涉及对象；
- 两个标记**可以叠在同一函数上**（`@func` + `@decor`），此时两种入口都开放、实现同一份；
- 只声明 `@func` 的点（`signals`、`settings` 这类纯条目点）**不开放 registrar**，
  用 `register("core/signals").add("progress", int, str)` 直接登记。

## registrar 只是语法糖

```python
@registrar("core/download/sources").add("origin")
class Origin(Template): ...

# 与下面完全等价
class Origin(Template): ...
register("core/download/sources").add(Origin, "origin")
```

装饰器形式的唯一作用是把「对象」延后到类创建完成才交给点；点拿到的调用永远是
`add(obj, name)`（`@decor`）或 `add(name, *args)`（`@func`）。所以 registrar 不需要
猜测参数、也不需要任何“先记标记、等 apply”的机制。

> 📌 条目的元数据（`title` / `icon` / `default`）由**点的契约**决定取哪些字段，
> 通常直接取被装饰对象的类属性（`name`、`icon`、`title_key`、`iconPath` 都会被认）；
> 不要往 registrar 里塞 `title=` / `icon=`，那是点的语义，不是通用入口的语义。
